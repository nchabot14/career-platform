# Ex05: Failed Network, DNS, or TLS Check

## Setting and prediction

This is the supplied simulation, not my real site.
The check that I am looking at is `dig site.lab.example` plus `curl -Iv https://site.lab.example/`.
I am expecting the DNS to point the name at Railway, and the HTTPS should work with the certificate for `site.lab.example`.

## Failed check and evidence

Failed check date: October 13, 2026.

This output is simulated, supplied by the assignment, and an output from a command I did not run.

Here are the two outputs from the commands:

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  A  198.51.100.24

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (198.51.100.24) port 443
* Server certificate: subject: CN=old-vm.lab.example
* SSL: certificate subject name does not match target host name 'site.lab.example'
curl: (60) SSL certificate problem: certificate subject name does not match target host name
```

What actually happened: When curl tried to connect to `https://site.lab.example/`, it reached the server at the address `198.51.100.24`, and then received a certificate issued for `old-vm.lab.example`, rather than the intended `site.lab.example`, causing it to refuse connection since the certificate names do not match.

## Diagnosis

DNS: The dig result shows that `site.lab.example` still has an A record pointing to the IP `198.51.100.24`, which is the old Azure VM's address. The DNS never got updated to point the name at the Railway deployment.

Connection: Since curl follows DNS, it connected to `198.51.100.24` on port 443, meaning the request was sent to the old VM instead of Railway.

Certificate: The old VM responded with its own certificate, issued for `old-vm.lab.example`, and since that name doesn't match the intended site, `site.lab.example`, curl rejected the certificate and failed the connection.

Cause: Even though the error message is about TLS, the certificate problem is a symptom, not the root cause. The real fault is that DNS sends visitors to the wrong server, and that server is connected via the wrong certificate.

Repair: Inside of cloudflare, I would delete the outdated A record for site and add a new record pointing `site.lab.example` to the current railway app, on DNS only. Once the name points at Railway, it should provide its own valid certificate for `site.lab.example`.

## Repair and repeated check

This is a simulated output, not one that I ran myself.

Output:

```
$ dig site.lab.example A +noall +answer
site.lab.example.  300  IN  CNAME  current-app.up.railway.app.
current-app.up.railway.app.  300  IN  A  203.0.113.44

$ curl -Iv https://site.lab.example/
* Connected to site.lab.example (203.0.113.44) port 443
* Server certificate: subject: CN=site.lab.example
* SSL certificate verify ok.
< HTTP/2 200
```

The follow up shows that the old A record pointing to `198.51.100.24` got replaced with a CNAME record pointing `site.lab.example` to `current-app.up.railway.app`, with the address `203.0.113.44`. This is an interpretation of the supplied output.

After the change was made, curl successfully connected to `203.0.113.44`, received a certificate for `site.lab.example`, and got a response from HTTP. This is similar to my proposed repair, which supports my diagnosis that DNS pointing to the old server is what caused the error.

## What you learned

A check that separates a DNS problem from a TLS or application problem is running `curl -I https://current-app.up.railway.app/` directly. If the Railway URL works but the domain fails, it proves that the app and its certificate are not the issue, but rather how the domain resolves.

A correct DNS answer by itself does not prove that the site is working, so checking HTTPS and confirming the page shows its intended result is a good habit to develop. It is not possible to call an issue fixed until you know for sure that the page is showing the correct information and content.
